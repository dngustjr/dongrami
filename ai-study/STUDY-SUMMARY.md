## 14/01 에이전트 루프

**한 줄 요약**: 에이전트는 "생각 → 도구 사용 → 결과 확인"을 일이 끝날 때까지 되풀이하는 반복 구조(ReAct)다.

**이 레슨이 풀려는 문제**
일반 챗봇은 질문 하나에 답 하나를 하고 끝난다. 하지만 실제 업무는 "조회해 보고, 그 결과를 보고 다음에 뭘 할지 정하는" 일의 연속이다. 이걸 스스로 하게 만드는 기본 틀이 필요하다.

**핵심 개념**
- **ReAct** = Reason(생각) + Act(행동). 매 턴마다 "생각 → 행동(도구 호출) → 관찰(결과)"을 반복한다.
- 비유: 신입 직원이 "주문부터 확인해야겠다(생각) → 주문 시스템 조회(행동) → 120건이네(관찰) → 그럼 재고를 봐야겠다..." 하고 일을 이어 가는 모습.
- 요즘은 "Thought:"라고 글로 적는 대신 모델이 내부 추론 채널을 따로 쓰지만, 반복 구조 자체는 같다.

**에이전트에 꼭 필요한 5가지** (하나라도 빠지면 챗봇)
| 요소 | 쉬운 설명 | 공구 예시 |
|---|---|---|
| 대화 기록 | 지금까지 한 일의 기록 | 고객 문의 → 조회 → 결과 |
| 도구 목록 | 쓸 수 있는 도구와 이름 | 주문조회, 재고조회, 환불접수 |
| 종료 조건 | 언제 끝낼지 | 답변을 완료했을 때 |
| 횟수 제한 | 무한 반복 방지 | 최대 20번 시도 |
| 결과 변환 | 도구 오류도 AI가 읽을 글로 바꿔 주기 | "재고 시스템 오류"라는 문장으로 전달 |

**공구 적용**: "이 고객 주문 상태 알려줘" → 주문 조회 → 배송 조회 → 답변 작성을 스스로 이어서 수행.

**주의할 점**
- 횟수 제한이 없으면 같은 행동을 무한 반복할 수 있다. 실제로 최대 횟수에 걸리는 경우를 코드로 확인했다.
- **도구가 가져온 글은 믿으면 안 되는 입력**이다. 웹/파일 안에 "전부 삭제해"라는 문장이 있어도 따르면 안 된다. 사용자가 직접 한 지시만 허가로 친다.
- 어떤 프레임워크(LangGraph, CrewAI 등)를 써도 속은 같은 반복이다. 차이는 그 주변 기능(저장, 역할 등)뿐이다.

## 14/02 ReWOO와 계획 후 실행

**한 줄 요약**: 계획자가 전체 계획을 먼저 짜고, 일꾼들이 실행하고, 해결자가 결과를 모아 답하는 방식이라 ReAct보다 토큰(비용)이 약 5분의 1이다.

**이 레슨이 풀려는 문제**
ReAct는 단계마다 이전 내용을 전부 다시 읽어서, 단계가 길어질수록 비용이 눈덩이처럼 커진다.

**핵심 개념**
- 세 역할: **계획자**(할 일 목록과 순서 작성) → **일꾼**(도구 실행, 동시 실행 가능) → **해결자**(계획+결과를 보고 최종 답).
- 계획 안에서 앞 단계 결과를 `#E1`, `#E2` 같은 이름표로 가리킨다. 예: "#E1(주문 목록)의 합계를 #E2(재고)와 비교".
- 비유: 장보기 전에 쪽지에 목록을 다 적고, 마트에서는 그냥 쪽지대로 담고, 집에 와서 요리하는 방식. ReAct는 한 칸 걸을 때마다 "다음에 뭘 살까" 다시 고민하는 방식.

**언제 무엇을 쓰나**
| 방식 | 알맞은 경우 | 공구 예시 |
|---|---|---|
| ReAct | 짧은 일, 상황이 계속 바뀜 | 고객 문의 응대 |
| ReWOO | 도구와 순서가 거의 정해진 일, 비용이 중요 | 주문 취합→발주서 작성 |
| Plan-and-Execute | ReWOO + 중간에 계획 수정 | 공급처 재고 부족 시 대체 |
| Plan-and-Act | 30단계 넘는 아주 긴 일 | 대규모 공구 오픈 준비 |

**주의할 점**
- 일꾼 하나가 실패하면 ReWOO는 "오류 문장"을 결과로 넘기고, 해결자가 그걸 보고 최대한 정리해서 답한다(실패가 그 한 칸에 국한됨).
- 한 번 도구 쓰고 요약하면 끝나는 단순한 일에는 과한 설계다. 단순한 것부터 시작한다.
- 계획자는 결과를 못 보므로 작은 모델로도 대체 가능(비용 절감).

## 14/03 Reflexion (실패에서 배우기)

**한 줄 요약**: 행동자가 시도하고, 평가자가 점수를 매기고, 반성자가 "왜 실패했는지"를 글로 적어 다음 시도 때 미리 읽게 하는 방식이다.

**이 레슨이 풀려는 문제**
AI는 대화가 끝나면 실패를 기억하지 못해서 같은 실수를 반복한다. 모델을 다시 훈련하지 않고도 "경험에서 배우게" 하고 싶다.

**핵심 개념**
- 세 역할 + 기억 한 가지: **행동자 → 평가자 → 반성자 → 반성문 저장소(에피소드 기억)**.
- 반성문 예: "고객이 묻은 건 '환불'이 아니라 '교환'이었는데 환불 절차로 안내했다. 앞으로는 먼저 요청 종류를 확인한다."
- 평가자 3종류: ① 외부 신호(성공/실패, 테스트 통과) – 가장 강함 ② 규칙 기반(같은 행동 두 번 = 막힘) ③ AI 자체 평가 – 가장 약함.

**공구 적용**: 응대 실패 사례를 반성문으로 저장해서 다음 응대 때 앞에 붙여 줌. Claude Code의 CLAUDE.md도 같은 원리(배운 것을 글로 적어 다음 세션에 읽힘).

**언제 잘 되고 안 되나**
- 잘 됨: 실패 신호가 분명하고, 같은 종류의 일이 반복되며, 다시 시도할 기회가 있을 때.
- 안 됨: 실패 신호가 없거나 일회성 일.

**주의할 점**
- **기억 부패(memory rot)**: 저장소가 사라진다는 뜻이 아니라, **낡았거나 틀린 반성문이 쌓여서 이후 시도를 잘못된 쪽으로 몰고 가는 것**. 대응책은 유효기간(TTL), 중복 제거, 압축.
- 외부에서 온 실패("공급처 서버 다운")와 자기 실수("잘못 읽음")를 구분해서 적어야 한다. 외부 실패까지 반성문에 쌓으면 쓸모없는 교훈이 늘어난다.

## 14/04 Tree of Thoughts와 LATS (여러 갈래 탐색)

**한 줄 요약**: 한 길로만 가지 않고 여러 생각을 가지처럼 펼쳐 점수가 높은 갈래를 더 깊이 파는 방식(ToT)이며, 실행 결과와 반성까지 합친 고급판이 LATS다.

**이 레슨이 풀려는 문제**
한 번의 사고 흐름이 틀린 방향으로 가면 되돌릴 수 없다. 여러 후보를 만들어 비교하면 어려운 문제에서 정답률이 크게 오른다(숫자 퍼즐에서 4% → 74%).

**핵심 개념**
- **ToT**: 각 생각(노드)을 여러 가지로 확장하고, AI가 점수를 매겨 좋은 길만 탐색.
- **LATS**: 행동 제안 + 점수 평가 + 실패 반성을 한꺼번에 쓰고, **실제 도구 결과**를 점수에 반영.
- **탐색의 균형**: 이미 좋아 보이는 길을 더 파기(활용) vs 안 가 본 길 시도(탐험). 이 균형 숫자(c)가 0에 가까우면 한 길만 판다.

**공구 적용**: 복잡한 가격·구성 결정에서 여러 안을 만들어 비교할 때.

**주의할 점**
- **비용 폭탄**: 일반 사고의 100~1000배 토큰. 우리 장난감 실험에서도 확장 비용 286 vs 152로 차이가 났다.
- **약한 채점은 위험**: 점수 기준이 허술하면(숫자를 다 안 써도 "좋은 해"로 인정 등) 엉뚱한 길을 열심히 판다.
- 쓸 만한 경우: 한 번으로는 부족한 어려운 일 + 시간보다 정확도가 중요 + **싸고 믿을 만한 채점 수단**(코드 테스트 등)이 있을 때만.

## 14/05 Self-Refine과 CRITIC (고쳐 쓰기)

**한 줄 요약**: Self-Refine은 AI가 스스로 검토해 고쳐 쓰는 방식이고, CRITIC은 검색·계산기·테스트 같은 **외부 도구로 사실 확인한 결과**로 고쳐 쓰는 방식이다.

**이 레슨이 풀려는 문제**
AI의 첫 답은 틀릴 수 있는데, 어떻게 더 좋게 만들 것인가.

**핵심 개념**
- **Self-Refine 흐름**: 초안 → 점검(비평) → 수정 → 점검 → 수정 … "문제 없음" 또는 횟수 소진 시 종료. 수정할 때 **지금까지의 모든 초안과 비평을 같이 보여 줘야** 같은 실수를 반복하지 않는다.
- **CRITIC**: 점검 단계를 "AI의 느낌"이 아니라 **도구 결과**로 대체. 사실은 검색, 계산은 계산기, 코드는 테스트.
- 비유: Self-Refine = 자기가 쓴 글을 자기가 다시 읽어 보기. CRITIC = 옆자리에서 원본 엑셀과 계산기로 대조해 주기.

**종료 조건 권장안**
외부 검증이 통과하면 종료. 검증이 없으면 "AI가 괜찮다고 함 + 최소 2번 이상 시도" 또는 "최대 횟수 도달"로 종료.

**공구 적용**: 공지문의 가격·마감일·수량은 원본 엑셀과 계산기로 대조(CRITIC). 문장 다듬기처럼 외부 기준이 없는 일은 Self-Refine으로 충분.

**주의할 점**
- **자기 점검의 함정**: 틀린 내용도 만든 본인에게는 그럴듯해 보여서 "괜찮다"고 하며 통과시킨다. 장난감 실험에서 Self-Refine이 4번 내내 같은 오답으로 굳어졌다.
- 외부 도구가 없는 일(창작, 서식)에서는 CRITIC도 사실상 Self-Refine과 같아진다.
- 이 패턴은 14/12의 "평가자-개선자" 워크플로의 원형이다.

## 14/06 도구 사용과 함수 호출

**한 줄 요약**: AI가 도구를 쓰려면 이름·설명·입력 형식이 적힌 "도구 설명서(스키마)"가 필요하고, AI가 낸 호출 값은 **그대로 믿지 말고 반드시 검증**해야 한다.

**이 레슨이 풀려는 문제**
AI가 도구를 잘못 고르거나, 엉뚱한 값을 넣거나, 없는 도구를 지어내면 업무 사고가 난다.

**핵심 개념**
- **도구 설명서(스키마)** 3가지: 이름, 설명("무엇을 하고 언제 쓰는지"), 입력 형식(어떤 칸에 어떤 종류의 값). 형식 표기 방식을 JSON이라 부르지만, 개념은 "주문서 양식"과 같다.
- **설명이 가장 중요**: AI는 설명을 읽고 도구를 고른다. 설명이 겹치거나 부실하면 엉뚱한 도구를 쓴다(가장 흔한 실패 원인).
- **입력 검증 4가지**: ① 종류 변환("5"를 숫자 5로, 모호하면 거부) ② 허용값 확인(상태는 '접수/처리중/완료'만) ③ 필수 칸 누락 시 AI에게 오류 문장 반환 ④ 날짜·이메일 형식 확인.
- 오류가 나도 프로그램이 멈추지 않고 "이 칸이 비었어요"라는 **관찰 문장**으로 돌려줘서 AI가 고치게 한다.

**공구 적용**
| 상황 | 올바른 처리 |
|---|---|
| 환불·결제·발주 같은 돈 나가는 도구 | 입력이 조금이라도 모호하면 **엄격히 거부** (숫자만 대충 뽑아 실행 금지) |
| 고객이 "비행기 표 예매해줘" (없는 도구) | 지어내지 말고 "그건 못 합니다"라고 답 |
| "3개"가 수량인지 모호할 때 | 되묻기 |

**주의할 점**
- 한 번 호출은 거의 해결된 문제. 실패는 **기억 이어가기, 앞 결과에 따라 도구 고르기, 20단계 넘는 긴 작업에서 흐려짐, 도구가 없을 때 거절하기**에 몰려 있다.
- 평가 기준은 "호출 문장이 같나"가 아니라 "실제로 상태가 바뀌었나"(파일이 만들어졌나)가 더 믿을 만하다.

## 14/07 메모리: 가상 컨텍스트 (MemGPT)

**한 줄 요약**: AI의 작업대(한 번에 볼 수 있는 분량)는 작으므로, 컴퓨터가 RAM과 디스크를 나누듯 "항상 보이는 기억(core)"과 "필요할 때 검색해서 꺼내는 창고(archival)"로 나눈다.

**이 레슨이 풀려는 문제**
대화가 길어지면 앞부분이 작업대에서 밀려나 AI가 잊어버린다. 며칠에 걸친 대화나 아주 긴 문서도 다뤄야 한다.

**핵심 개념**
| 컴퓨터 개념 | MemGPT 개념 | 비유 |
|---|---|---|
| RAM | 메인 컨텍스트 (프롬프트) | 책상 위에 펼친 자료 |
| 디스크 | 외부 기억 (검색 저장소) | 서랍과 창고 |
| 페이지 폴트 | 기억 도구 호출 | "창고에서 꺼내 오겠습니다" |
| 운영체제 | 제어 반복 | 비서 |

- **인터럽트 패턴**: 응대 도중 AI가 기억 검색 도구를 부르면, 실행 결과가 다음 말에 끼워져 들어간다. 책상에서 일어나 창고를 다녀오는 것과 같다.
- 기억 도구: 핵심 기억 추가/수정, 창고 저장/검색, 지난 대화 검색.
- MemGPT는 2024년 Letta로 이어졌다(3단계 기억, 수면 에이전트 등은 14/08).

**공구 적용**
- **core(항상 보임)**: 고객 알레르기, 배송지, 사업 규칙.
- **archival(검색해서 꺼냄)**: 지난 주문 이력, 오래된 문의 내용.

**주의할 점**
- **중요한 정보를 창고에만 두면 AI가 검색해야 한다는 걸 모르고 지나쳐 놓친다.** 알레르기처럼 안 보이면 사고 나는 정보는 반드시 core에.
- **기억 오염**: 틀린 정보가 저장되면 이후 모든 응대에 영향을 준다.
- 메시지가 밀려나도 core는 남고 창고 검색으로 사실을 되찾는 것을 코드로 확인했다.

## 14/08 메모리 블록과 수면 시간 계산 (Sleep-time compute)

**한 줄 요약**: 기억을 역할별 칸(블록)으로 나누고, 일하지 않는 시간에 "수면 에이전트"가 기억을 정리한다.

**이 레슨이 풀려는 문제**
기억을 한 덩어리로 두면 뒤죽박죽이 된다. 또 기억 정리를 응대 중에 하면 고객이 기다려야 한다.

**핵심 개념**
- **블록 4종**: Human(고객 정보), Persona(AI의 성격·말투), Task(지금 하는 일), Safety(절대 지킬 규칙). 비유: 서류철 4개.
- **3단계 기억**: core(항상 보임) / recall(최근 대화 기록, 검색) / archival(장기 창고).
- **블록 상한**: 칸마다 글자 수 한도가 있다. 한도에 가까워지면(경고선, 예: 176자) 요약하도록 유도하고, 가득 차면 더 못 받는다.
- **수면 에이전트**: 응대하는 AI와 별도로, **일 안 하는 시간에** 대화 기록을 읽고 기억 블록을 정리·요약·모순 해소한다. 대기 시간 밖에서 돌기 때문에 **더 똑똑하고 느린 모델**을 써도 된다.

**공구 적용**: 낮에는 응대 AI가 빠르게 답하고, 밤에는 수면 에이전트가 그날 고객들의 선호·불만을 고객 블록에 정리.

**주의할 점**
- 블록이 꽉 차면 **오래됐지만 중요한 정보가 요약 과정에서 사라질 수 있다.** 장난감 요약기는 마침표 없는 긴 글을 통째로 날려 버렸다.
- **조용한 어긋남(silent drift)**: 정리하다가 틀린 요약이 들어가도 아무도 눈치채지 못한다. 정기 점검이 필요.
- 수면 에이전트가 언제 돌지, 모순 중 어느 것을 남길지는 **사람이 정해 줘야** 하는 부분이다(자동으로 알아서 되지 않음).

## 14/09 하이브리드 메모리 (Mem0)

**한 줄 요약**: 기억을 벡터(비슷한 것 찾기), KV(정확한 값), 그래프(관계) 세 저장소에 나눠 저장하고, 꺼낼 때는 관련도·중요도·최신성 점수를 합쳐 고른다.

**이 레슨이 풀려는 문제**
한 종류의 저장소로는 모든 질문에 답할 수 없다. "배송 며칠 걸려요?"와 "같은 건물 사는 고객이 누구야?"는 필요한 저장 방식이 다르다.

**핵심 개념**
| 저장소 | 잘하는 질문 | 공구 예시 |
|---|---|---|
| 벡터 | 의미가 비슷한 내용 찾기 | "비슷한 불만 사례" |
| KV (이름-값) | 정확한 값 한 개 | "고객 A의 배송 소요일 = 2일" |
| 그래프 | 관계 따라가기 | "같은 건물에 사는 고객들" |

- 새 기억 추가 시 세 저장소에 **동시에 기록**하고, AI가 대화에서 사실(값, 관계, 중요도)을 **자동으로 뽑아낸다**.
- **꺼내는 점수 = 관련도 + 중요도 + 최신성**. 문의 응대는 "방금 한 말"이 가장 중요하므로 **최신성 가중치를 가장 높게**.
- **범위(scope)**: 사용자 단위 / 세션 단위 / 에이전트 단위로 나눠 섞이지 않게.
- **Mem0g의 소프트 무효화**: 정보가 바뀌면 옛 기록을 지우지 않고 "더 이상 유효하지 않음"으로 표시.

**주의할 점**
- **무효화는 세 저장소 모두에 연결해야 한다.** 그래프에서만 "베를린→이사함"을 표시해도, 통합 검색이 그걸 후보 선정에 쓰지 않으면 옛 주소가 계속 나온다(우리가 직접 틀렸던 부분).
- **임베딩 드리프트**: 의미 검색용 숫자 변환 모델을 바꾸면 옛 기록과 새 기록이 호환되지 않음 → 자주 쓰는 기록부터 다시 변환.
- LLM이 사실을 자동으로 뽑는 과정에서 틀린 사실이 저장될 수 있다(14/07의 기억 오염과 연결).

## 14/10 스킬 라이브러리와 평생 학습 (Voyager)

**한 줄 요약**: 성공한 방법을 실행 가능한 코드 "스킬"로 이름 붙여 저장하고, 새 일이 오면 검색해서 꺼내 쓰고 조합한다.

**이 레슨이 풀려는 문제**
에이전트가 같은 일을 할 때마다 처음부터 다시 방법을 찾는 건 낭비다. 한 번 성공한 방법을 쌓아서 점점 더 큰 일을 해내게 하고 싶다. (원래는 마인크래프트를 하는 AI 연구.)

**핵심 개념 (신입 직원 비유)**
| 구성요소 | 비유 | 하는 일 |
|---|---|---|
| 자동 커리큘럼 | 선배가 "이제 이걸 해 봐" 정해 주기 | 지금 능력보다 **살짝 어려운** 과제를 고름 |
| 스킬 라이브러리 | 업무 매뉴얼 모음 | 성공한 방법을 이름 붙여 저장·검색 |
| 반복 프롬프팅 | 해 보고 틀린 곳 고쳐 재시도 | 실행 결과·오류를 보고 코드를 수정 |

- **행동의 단위가 "실행 가능한 코드"**라서 저장·검색·조합이 쉽다("주문 엑셀 읽기" + "상품별 취합" → "발주서 만들기").
- **세 가지 실행 신호**(성공/오류/화면 상태 변화)로 스킬이 제대로 됐는지 판단.
- 새 스킬을 저장할 때는 **중복 확인**(비슷한 게 이미 있나)을 거친다.
- Claude Agent SDK의 스킬 기능이 이 구조와 같다.

**공구 적용**: "주문 엑셀 정보 받아오기" 같은 반복 작업을 스킬로 쌓고, 큰 일은 스킬을 조합해서 처리.

**주의할 점**
- **조합 드리프트**: 부모 스킬이 자식 스킬의 "최신 버전"을 몰래 불러 쓰면, 자식이 바뀌었을 때 부모가 예고 없이 오작동. → **버전 고정(pin)**.
- **스킬이 많아지면 비슷한 스킬 구분이 어려움** → 태그 필터로 후보를 좁혀서 검색.
- 중복 저장을 막지 않으면 라이브러리가 지저분해진다.

## 14/11 HTN 계획과 진화 검색

**한 줄 요약**: HTN은 큰 일을 "시작 조건"이 붙은 단계로 쪼개 순서가 틀릴 수 없게 하는 계획법(AI 제안은 조건 검사를 통과한 것만 채택)이고, 진화 검색은 AI가 변형을 만들고 기계가 매기는 정확한 점수로 좋은 것만 남기며 개선하는 방법이다.

**이 레슨이 풀려는 문제**
두 가지 계획이 기존 방식으로는 부족하다. ① **절대 틀리면 안 되는 절차**(결제, 환불, 준수 업무) ② **숫자로 잴 수 있는 "최선"을 찾는 일**(비용 절감, 최적화).

**1) HTN (계층형 작업 계획)**
- 구성: **작업**(쪼갤 큰 일/바로 할 작은 일), **방법**(큰 일을 쪼개는 규칙, 조건 포함), **연산자**(실제 행동, 조건과 결과 정의), **상태**(지금 사실들).
- 핵심: 각 단계에 **시작 조건**이 있고, 조건이 안 맞으면 실행되지 않으므로 **계획이 틀릴 수 없다**.
- 예: 발주서 전송의 조건은 "결제 확인 완료", 결제 확인의 조건은 "주문 취합 완료".
- **ChatHTN**: 규칙집에 없는 새 상황이면 AI에게 "어떻게 쪼갤까?" 물어본다. 단 AI의 답은 **제안일 뿐**이고 조건 검사를 통과해야 채택. AI가 그럴듯하게 틀린 단계를 지어내도 걸러진다.
- 한 번 정해진 방법은 **저장(캐시)**해서 다음부터는 AI를 안 부른다(실험: AI 호출 1회 → 이후 0회).

**2) 진화 검색 (AlphaEvolve)**
- 반복: 시작안 준비 → AI가 변형 여러 개 생성 → **자동 채점기**가 점수 → 좋은 것만 남겨 다시 변형.
- 실험: 점수(오차)가 286 → 99 → 6세대에 0으로 정답 도달.
- 실제 성과: 행렬 곱셈에서 56년 만의 개선, 구글 서버 자원 0.7% 절감 등.
- **절대 조건: 채점기가 기계로 정확히 점수를 낼 수 있어야 한다.**

**언제 무엇을 쓰나**
| 문제 | 방법 | 이유 |
|---|---|---|
| 순서 엄수 절차(환불 승인 후에만 입금) | HTN | 조건으로 정책을 강제 |
| 택배비 최소화 | 진화 검색 | 실제 청구액으로 점수화 |
| 여러 단계 일반 업무 | ReAct/ReWOO | 보장은 없지만 유연 |
| 문구가 "매력적인지" | (진화 검색 부적합) | 자동 채점이 어려움. 클릭률처럼 숫자로 재는 값을 점수로 정하면 가능 |

**주의할 점**
- **조건(연산자) 정의가 없는 HTN**은 안전 보장이 무너진다.
- **"AI에게 더 나은지 물어보기"는 채점기가 아니다.** 같은 질문에도 답이 달라 기준이 흔들린다.
- 대부분의 업무에는 둘 다 과하다. 먼저 ReAct/ReWOO를 쓰고, 정말 필요할 때만.

## 14/12 Anthropic의 워크플로 패턴 (단순한 게 낫다)

**한 줄 요약**: 순서를 미리 적을 수 있으면 워크플로(사람이 정한 고정 경로)로 시작하고, 순서를 모를 때만 에이전트(AI가 경로를 정함)를 쓴다. 워크플로 기본형은 다섯 가지다.

**이 레슨이 풀려는 문제**
많은 팀이 한 번의 호출로 될 일에 복잡한 멀티 에이전트 프레임워크를 들여와서 비용, 디버깅 난이도, 불투명성만 키운다.

**워크플로 vs 에이전트**
| | 워크플로 | 에이전트 |
|---|---|---|
| 비유 | 레시피대로 만드는 주방 | 손님 요청에 맞춰 알아서 메뉴를 짜는 셰프 |
| 순서 결정 | 사람 | AI |
| 장점 | 싸고 빠르고 원인 찾기 쉬움, 감사 대응 가능 | 예측 못 한 상황에 대응 |
| 단점 | 틀 밖은 못 함 | 비용이 불어나고 실패 원인 찾기 어려움 |

**다섯 가지 워크플로 패턴**
| # | 패턴 | 설명 | 공구 예시 |
|---|---|---|---|
| 1 | 체인 | 앞 결과가 다음 단계 입력 | 주문 읽기→취합→발주서→전송 |
| 2 | 라우팅 | 분류해서 담당에게 배분 | 문의를 배송/환불/상품으로 나눠 각 담당 AI에게 |
| 3 | 병렬 | 나눠서 동시에, 또는 같은 걸 여러 번 시켜 다수결 | 상품 100개 설명 분할 작성, 환불 판단 5번 다수결 |
| 4 | 오케스트레이터-워커 | 지휘자 AI가 필요한 일꾼을 그때그때 골라 시킴 | "공구 오픈 준비" → 상세페이지/공지/재고 일꾼 배정 |
| 5 | 평가자-개선자 | 쓰고 → 점검 → 통과할 때까지 반복 | 공지문 초안→마감일 누락 지적→수정 |

**선택 기준**
- 워크플로가 좋은 경우: 단계를 미리 다 적을 수 있음(발주·정산), 비용 상한이 중요, 나중에 설명해야 함(분쟁).
- 에이전트가 좋은 경우: 앞 결과에 따라 다음이 달라짐(새 공급처 조사), 일의 길이를 모름, 새 분야.

**핵심 원칙**: 새 업무는 에이전트로 탐색한 뒤, 절차가 굳어지면 워크플로로 고정한다.

**주의할 점**
- 다섯 패턴을 다 합쳐도 AI 호출 20번 정도이고, 프레임워크 없이 직접 호출로 충분했다.
- 병렬 다수결은 AI가 가끔 엉뚱하게 답하는 위험을 줄여 주지만 호출 비용이 N배.
- 프레임워크는 저장 상태(LangGraph), 동시 실행(AutoGen), 역할 틀(CrewAI)이 **진짜 필요할 때만** 도입한다.

## 14/13 상태 그래프와 체크포인트 (LangGraph)

**한 줄 요약**: 업무를 "칸(노드)과 길(엣지)이 있는 지도"로 그리고, 칸이 끝날 때마다 작업 일지(상태)를 통째로 저장해서 중간에 끊겨도 마지막 성공 지점부터 이어서 하고, 원하는 칸 앞에서 사람이 확인·승인하게 할 수 있다.

**이 레슨이 풀려는 문제**
40단계 작업이 38단계에서 실패했을 때 처음부터 다시 하면 시간과 비용이 두 배가 되고, 이미 한 일(발주, 전송)을 또 하는 사고가 날 수 있다.

**핵심 개념 (게임 세이브 포인트 비유)**
| 부품 | 쉬운 설명 | 공구 예시 |
|---|---|---|
| 상태 | 진행 기록이 담긴 작업 일지 | 주문 수, 분류 결과, 승인 여부, 최종 결과 |
| 노드 | 한 가지 일을 하는 칸 | 분류 / 환불 처리 / 사람 승인 / 전송 |
| 엣지 | 다음 칸으로 가는 길 | 분류 다음은 전송 |
| 조건 엣지 | 일지를 보고 갈림길 선택 | 분류가 '환불'이면 환불 칸으로 |
| 체크포인터 | 칸이 끝날 때마다 일지를 통째로 저장하는 저장소 | 세이브 슬롯 |

- **지속 실행(durable execution)**: 중간에 멈춰도 "이 세션 이어서"라고 하면 마지막 성공 칸 다음부터 정확히 이어진다. 실제 큰 회사들이 이 이유로 쓴다.
- **사람이 끼어드는 자리(human-in-the-loop)**: 특정 칸 앞에서 일부러 멈추고, 사람이 일지를 확인·수정한 뒤 이어서 진행. 저장되어 있기 때문에 가능하다.
- **그 밖의 기능**: 칸마다 중간 결과를 흘려 보내기(스트리밍), 짧은 기억(한 번의 실행 안)과 긴 기억(여러 번 실행에 걸침).
- **여러 에이전트를 묶는 3가지 구조**: 감독자(팀장이 분배) / 스웜(동료끼리 직접 넘김) / 계층형(팀장 밑에 파트장, 그래프 안에 작은 그래프).

**공구 적용**
- 주문 1,000건 처리 중간에 끊겨도 처음부터 다시 하지 않는다.
- "발주서 전송 칸 앞에서 정지 → 사장님이 금액 확인 → 승인하면 이어서 전송". 실행 실험에서 승인 전후로 접수 번호가 그대로여서 중복 생성이 없음을 확인했다.

**주의할 점**
- **일지 일부만 저장하면 위험**: 대화만 저장하고 "어디까지 발주했는지" 같은 도구 상태를 저장하지 않으면, 이어서 할 때 이미 한 발주를 모르고 **중복 발주**한다. 승인 여부, 외부에서 받은 값(환율·재고 수), 결제·전송 이력도 반드시 같이 저장.
- **실행할 때마다 결과가 달라지는 칸**(현재 시각, 외부 시스템 응답, 무작위): 이어 하기는 "같은 입력이면 같은 결과"를 전제하므로, 그런 값은 일지에 적어 두어야 어긋나지 않는다.
- **갈림길 남발**: 모든 길이 조건부면 지도가 스파게티가 된다. 기본은 일직선, 갈림길은 가끔.
- 도구 선택: 저장 상태가 중요하면 LangGraph, 동시 처리가 많으면 AutoGen, Claude Agent SDK는 세션 저장이 기본 제공.

## 14/14 액터 모델 (AutoGen)

**한 줄 요약**: 에이전트를 "개인 서랍과 우편함을 가진 직원"으로 보고, 서로 우편함 메모로만 소통하게 하면 한 명이 실패해도 팀 전체가 멈추지 않고 여러 일이 동시에 진행된다.

**이 레슨이 풀려는 문제**
에이전트들이 전화 통화처럼 한 명이 다른 한 명의 답을 기다리는 구조면, 상대가 느리거나 쓰러질 때 같이 멈춘다. 동시에 여러 명에게 일을 시키기도 어렵고, 팀을 여러 컴퓨터로 넓히려면 처음부터 다시 만들어야 한다.

**핵심 개념 (우편함 있는 사무실 비유)**
| 전화 방식 | 우편함 방식 |
|---|---|
| A가 B에게 전화하고 답이 올 때까지 수화기를 들고 대기 | A가 B의 우편함에 메모를 넣고 바로 자기 일로 복귀 |
| B가 쓰러지면 A도 막힘 | B가 쓰러져도 A는 계속 일함 |
| 한 번에 한 명씩 순서대로 | 여러 메모가 동시에 오가며 각자 속도로 처리 |

| 액터의 3요소 | 쉬운 설명 | 공구 예시 |
|---|---|---|
| 개인 서랍(상태) | 본인만 열 수 있는 메모장 | 발주 담당의 발주 내역을 응대 담당이 몰래 못 고침 |
| 우편함(인박스) | 처리할 메모가 쌓이는 곳 | 주문 취합 끝 메모가 발주 담당 우편함에 쌓임 |
| 처리 방법(핸들러) | 메모를 받으면 하는 일 | 답장하기, 다른 직원에게 전달, 새 직원 투입 |

- **장애 격리**: 한 직원의 처리 중 오류는 그 직원의 메모 하나에서만 끝난다. 운영 시스템(런타임)이 오류를 잡아 기록한다.
- **처리 못 한 메모함(dead-letter)**: 실패한 메모를 버리지 않고 따로 보관해서 사람이 원인을 보고 다시 처리할 수 있게 한다.
- **AutoGen의 세 층**: Core(우편 인프라) / AgentChat(팀 편성 도구) / Extensions(외부 연결).
- **팀 운영 두 가지**: 돌아가며 말하기(RoundRobin, 정해진 순서) / 진행자가 지목(Selector, 상황 보고 담당 선택). Magentic-One은 웹·코드·파일을 다루는 마이크로소프트의 시범 팀.
- **현재 상태**: AutoGen은 유지보수 모드이고 후속은 Microsoft Agent Framework. 하지만 우편함 방식 아이디어는 그대로 쓰인다.

**공구 적용**
- 마감일 변경을 공지·환불·발주 담당에게 동시에 메모로 보내면, 한 명이 늦어도 나머지는 각자 처리한다.
- 실행 실험: 검토 담당에게 일부러 고장 메모를 보냈더니 그 1건만 처리 못 한 메모함으로 가고, 나머지 3건은 정상 처리되어 결과가 돌아왔다.

**주의할 점**
- 답이 즉시 필요한 일에는 우편함 방식이 오히려 번거롭다. 순서가 정해진 단순 업무는 워크플로가 낫다.
- 처리 못 한 메모함을 아무도 안 보면 실패가 조용히 쌓인다. 정기적으로 확인하는 사람(또는 알림)이 필요하다.
- 직원이 서로의 서랍을 못 보므로, 같이 알아야 할 정보는 메모로 명시해서 보내야 한다.
